# The hard problems in booking software

A booking form looks like a form. Underneath, it is a small distributed system that has to agree about time with people in other timezones, other calendars, other websites and other mail servers. This document lists the problems every booking system runs into, why each is harder than it looks, and what this build does about it. Where a problem is only partly solved, it says so.

---

## 1. Double booking

**The problem.** Two visitors load the same page and both see 10:00 free. Both submit. If the server checks "is 10:00 taken?" and then inserts, both checks can pass before either insert lands. The race window is milliseconds, but popular slots (the first Saturday of the month, a newly opened calendar) attract exactly this traffic. A unique index on the start time does not help once services have different lengths: a 60-minute booking at 10:00 and a 30-minute booking at 10:30 start at different times but overlap.

**What this build does.** Booking runs inside an SQLite `BEGIN IMMEDIATE` transaction, which takes the write lock before reading. Inside it, the server recomputes the whole list of open slots for that day and accepts the request only if the exact start time is still on it ([bookings.ts](../src/server/bookings.ts)). Overlap is checked as intervals (`start < other.end && other.start < end`), not as matching start times, and buffers are applied on both sides. Admin bookings and reschedules use the same overlap check inside their own transactions.

**Verified:** ten simultaneous requests for one slot produced exactly one booking and nine `409 That time has just been taken` responses, which the UI turns into a "pick another time" button.

**Limit.** This relies on SQLite serialising writers. Moving to Postgres would need the same check under `SERIALIZABLE` isolation or an exclusion constraint on a time range.

## 2. Time zones and daylight saving

**The problem.** "Open 09:00 to 17:00" means 09:00 *where the business is*, but the server may run in UTC, the visitor may be abroad, and the business may change its clocks twice a year. Common failures:

- Storing local times without a zone, so a booking silently moves an hour at the DST change.
- Generating slots by adding 30 minutes to a UTC instant, which drifts off the wall clock across a transition.
- Using `new Date('2026-03-29')`, which is midnight UTC and may be the previous day locally.
- On the night clocks spring forward, 01:30 does not exist. In autumn, 01:30 happens twice.

The original app had every one of these: it hardcoded `Africa/Windhoek` and computed weekdays in the server's zone.

**What this build does.** All booking instants are stored as UTC ISO strings. Calendar dates (`2026-03-29`) are handled as plain strings and their weekday is computed without any timezone. Slots are generated by walking *wall-clock* minutes in the business's IANA zone and converting each one to an instant with `@date-fns/tz` ([availability.ts](../src/lib/availability.ts)). Service length is measured in real elapsed time, so a 60-minute session is 60 minutes even across a transition. Tests cover the London spring-forward and fall-back days.

Customers see times in the business's zone, with a note when their own browser is in a different one ("times are in Europe/London"), because that is where they need to turn up.

**Limit.** For remote services (video calls), showing times in the visitor's zone would be kinder. That is a per-service display option worth adding.

## 3. Modelling availability

**The problem.** Real availability is not "Monday to Friday, 9 to 5". It is a lunch break, Saturday mornings only, a 15-minute clean-up between clients, no same-day bookings, nothing more than three months out, a week off in December, a 45-minute service that should be offered on the half hour. Every rule interacts with the others, and businesses will not edit code to express them.

**What this build does.** The slot engine is a pure function that takes all of these as inputs: weekly ranges (any number per day), time off as date ranges, existing bookings, service duration, slot interval, buffer, minimum notice and the advance window ([getSlots](../src/lib/availability.ts)). It is unit-tested in isolation. Each input is a field in the admin. The same function both draws the slot grid and validates a submitted booking, so the two can never disagree.

**Limit.** There is one shared calendar: no per-staff schedules, no resources (rooms, equipment), no service-specific hours. Those are the next layer of complexity and need a `staff` dimension on rules and bookings.

## 4. Spam, bots and abuse

**The problem.** A public form that sends email and holds slots is a target. Bots fill forms; pranksters book every slot for a week; scripts use the form to send email to arbitrary addresses. A CAPTCHA stops some of that but costs real customers conversions and, for most CAPTCHA providers, sends their data to a third party.

**What this build does.** Several cheap layers, none of which bothers a real person:

- A hidden honeypot field that only bots fill in.
- Per-IP rate limits on booking and slot lookups, using the IP your own proxy recorded rather than one the client claims ([rate-limit.ts](../src/server/rate-limit.ts)).
- A per-email limit of three new requests an hour.
- A short list of disposable email domains.
- Approval mode, on by default: a request holds the slot but the owner confirms it.
- Server-side validation of every field, with length caps.

**Limit.** These raise the cost of abuse; they do not stop a determined attacker using many IPs. The rate limiter lives in memory, which is correct only because SQLite means one process. **Run it behind a reverse proxy and set `TRUST_PROXY_HOPS`**: without a proxy, the client controls `X-Forwarded-For` and can sidestep the per-IP limit (the per-email limit and the slot lock still hold). A CAPTCHA hook for installs that get targeted is a sensible addition.

## 5. No-shows and cancellations

**The problem.** A booking is a promise with no cost to break. No-shows waste a slot that someone else wanted. If cancelling is hard, people just don't turn up; if it is too easy, slots churn.

**What this build does.** Every confirmation email carries a private link to view and cancel, and cancelling frees the slot immediately and emails the owner. Confirmations include an `.ics` invite so the booking lands in the customer's own calendar, which is the single most effective no-show reducer. The owner can set a booking policy shown above the booking button, and a minimum notice period.

**Limit.** No deposits, no reminder emails, no cut-off for late cancellations. Reminders need a scheduled job (cron or a queue), which is the most valuable next feature here. Deposits mean taking payments (see section 12).

## 6. Calendar sync

**The problem.** The owner lives in Google Calendar, not in this admin. Two-way sync sounds simple and is not: events created on the other side, edits on both sides, deleted events, recurring events, tokens that expire or get revoked, API rate limits, and partial failures where the booking saved but the calendar call failed.

**What this build does.** One-way sync, done reliably. Confirmed bookings create events; moves update them; cancellations and declines delete them ([google-calendar.ts](../src/server/google-calendar.ts)). Calendar calls run *after* the booking has been committed and after the response is sent, and a failure is logged without ever failing the booking. If Google reports the grant was revoked, the integration is marked as errored and the admin shows a reconnect prompt instead of the app hammering a dead token. Tokens are encrypted at rest, refreshed tokens are written back, and the OAuth flow is protected against CSRF.

**Limit.** Events added directly in Google (a dentist appointment, a day off) do not block slots here. The fix is to read the owner's free/busy for the day being viewed and treat it as extra busy intervals. The slot engine already accepts them, so this is a contained change, but it adds a Google API call to every slot lookup and needs caching.

## 7. Getting email delivered

**The problem.** Transactional email lands in spam unless it comes from a domain with SPF, DKIM and DMARC set up, through a provider with a good reputation. Sending from a server's own IP almost always fails. Email is also slow and flaky, and a booking must not fail because a mail server timed out.

**What this build does.** Email sits behind a small provider interface with SMTP and Resend implementations, chosen by environment variable ([mailer.ts](../src/server/email/mailer.ts)). With no provider configured, messages go to the log and the admin shows a warning, so a fresh install works without silently pretending to email anyone. Sending happens after the response via `after()`. A "send a test email" button proves the setup end to end. `Reply-To` is the business's public address, so customer replies reach a human.

**Limit.** There is no retry queue. A message that fails is logged and lost. A small outbox table with retries would close that gap. Domain authentication is the installer's job and is documented, not automated.

## 8. Living inside someone else's website

**The problem.** Businesses want the booking form on their own site, built with Wix, Squarespace, WordPress or Pixpa, where you control none of the page. Scripts injected directly into their page clash with their CSS and JavaScript and can read their visitors' data. Iframes avoid that but bring their own trouble: fixed heights that clip or leave gaps, third-party cookie blocking, and clickjacking if any page may frame you.

**What this build does.** The widget is an iframe of `/embed`, loaded by a tiny dependency-free `embed.js`. The embedded page reports its content height with a `ResizeObserver`; the loader accepts that message only from the booking origin and only from its own iframe, then resizes ([embed.js](../public/embed.js)). The booking flow needs no cookies at all, so third-party cookie blocking does not affect it. Only `/embed` may be framed, and `EMBED_ALLOWED_ORIGINS` can restrict that to the business's own domain; every other page sends `frame-ancestors 'none'`. The "view or cancel" link breaks out of the frame with `target="_top"`.

## 9. White-label configuration without code

**The problem.** A system rebuilt per customer is consultancy, not a product. Every hardcoded string, price, colour or timezone is a fork waiting to happen. But unlimited customisation produces unreadable colour schemes and broken layouts, and the support burden lands on whoever runs the platform.

**What this build does.** Every business-specific value lives in the database and is edited in the admin: identity, contact details, timezone, locale, currency, services, hours, rules, colours, typefaces, policy text. The environment holds only deployment concerns. Theming is deliberately narrow: three colours and a choice of four tested typeface pairs, from which the rest of the palette is derived. Text/background pairs below WCAG AA contrast are rejected with the measured ratio shown, so a business cannot ship an unreadable booking page. Prices and dates are formatted with `Intl` for the chosen locale and currency.

**Limit.** One install serves one business. Hosting many businesses from one deployment (true multi-tenant SaaS) needs a tenant id on every table, per-tenant domains, and per-tenant secrets. The domain layer is structured so that would be a contained change, but it has not been done.

## 10. Personal data and privacy

**The problem.** A booking system stores names, emails, phone numbers and often health or personal notes ("left hamstring, recovering"). Laws such as GDPR and South Africa's POPIA (and Namibia's emerging equivalent) require collecting only what is needed, protecting it, and erasing it on request. Third-party fonts, analytics and CAPTCHAs leak visitor data to other companies.

**What this build does.**

- **Erasure.** Each booking has an "erase personal data" action that blanks name, email, phone, location and notes while keeping the time slot and service, so history and reports stay intact.
- **Self-hosting.** Data stays in one file on infrastructure the business chooses.
- **No third-party requests.** Fonts are self-hosted at build time; there is no analytics and no CAPTCHA, so visitors' browsers talk only to this server.
- **Protected at rest.** Integration tokens are encrypted.
- **Private pages.** Admin and manage pages are `no-store` and `noindex`.
- **Unguessable links.** Manage links are 256-bit random tokens.

**Limit.** There is no automatic retention policy (for example, erase bookings older than two years), no customer data export, and the database file itself is not encrypted. Disk encryption on the host covers the last point.

## 11. Data safety, hosting and backups

**The problem.** The booking data is the business. Losing it, or running two copies that disagree, is worse than downtime. Hosted databases solve backups but add cost, latency, another account and another secret. The original app's Supabase password was committed to git.

**What this build does.** SQLite in WAL mode: one file, no server, no network hop, no credentials. Migrations are generated from the schema and run automatically on start. The Docker image stores data on a `/data` volume and has a health check. The README documents an online backup command.

**Limit.** SQLite means one instance with a persistent disk. Serverless platforms that discard the filesystem (Vercel, Netlify functions) cannot run it. For a single business that is the right trade: a small VPS handles far more bookings than any one business takes. For hands-off continuous backup, Litestream can stream the file to object storage.

---

## 12. Secrets management

**The problem.** Booking systems accumulate secrets: database credentials, session keys, OAuth client secrets, SMTP passwords, API keys. Every one that is committed, logged or shared in a screenshot is a breach waiting to happen, and git never forgets.

**What happened here.** The original repository contained a live database connection string and the owner's password in a setup script. Removing the file does not remove it from history.

**What this build does.** No secret exists in code. One `APP_SECRET` is the root: sessions, OAuth state and token encryption all derive separate keys from it with HKDF ([crypto.ts](../src/server/crypto.ts)). Production refuses to start without it, instead of falling back to a default. `.env*` files are git-ignored except the documented example. Development generates a throwaway secret on first run, so nobody is tempted to commit one.

**What still has to be done by hand:** rotate the leaked Supabase password (or delete that project), and change the leaked admin password anywhere it is reused. Optionally rewrite history with `git filter-repo`; rotation is what actually protects you.

## Known gaps

Things a growing business will ask for that this build does not do yet, roughly in order of value:

1. **Reminder emails** a day before, which need a scheduler.
2. **Reading Google free/busy** so personal events block slots.
3. **Multiple staff** with their own hours, and resources like rooms.
4. **Payments and deposits.** This also brings PCI scope, refunds and failed payments, so it belongs with a provider such as Stripe Checkout rather than built in.
5. **Email retry queue.**
6. **Multiple admin users with roles.** Today every admin can do everything.
7. **Multi-tenant hosting** of many businesses in one deployment.
